04 · Exclusivo del ERP
Hallazgos de diseño y verificación del sistema privado. Son independientes de la lógica de cobro de la tienda.

has_permission y autorización efectiva

Debe comprobarse que el permiso se resuelva en base de datos, por organización, rol, excepción y alcance operativo; ocultar controles no alcanza. La evidencia disponible muestra contratos y pruebas, pero no una ejecución runtime completa.

pgTAP y puerta de base local

La preocupación por fallos de pgTAP queda como punto de auditoría. El estado verificable actual es PENDING: npm run db:test no pudo conectar a 127.0.0.1:54322 porque Docker no estaba disponible. Los conteos y causas quedan sin afirmar.

Seed consistente y reconstruible

supabase/seed.sql debe permanecer determinista, idempotente y coherente con migraciones, permisos y datos de prueba. La revisión de una base vacía requiere levantar el stack local; no se ejecutó un reset destructivo.

Módulos todavía pendientes

El programa contempla compras, ventas, reparaciones, documentos, financiación, contabilidad, reportes y migración. Las pantallas actuales no prueban por sí solas libros, reversas, auditoría, observabilidad ni conciliación completa.

Docker y entorno local

La ruta de verificación depende del daemon Linux de Docker. Mientras no esté disponible, SQL, RPC, RLS y pgTAP no tienen validación runtime local. Supabase remoto queda fuera de alcance sin autorización expresa.

05 · Mercado Pago, paso a paso
El flujo observado en el sistema existente conserva una frontera clara: el navegador inicia, el servidor recalcula y Mercado Pago notifica el resultado.

Checkout

Valida carrito al entrar y nuevamente antes de pagar. Recibe datos del comprador y solicita la preferencia.

Preferencia

La Edge Function busca precio, nombre y stock reales; no confía en el precio enviado por frontend.

Mercado Pago

Crea la preferencia, define retornos success/failure/pending y redirige al comprador a init_point.

Webhook

El proveedor llama sin JWT de Supabase. La función debe verificar su firma HMAC propia cuando existe el secreto.

Pedido y stock

Consulta el pago, actualiza el pedido, reclama una sola vez el decremento y llama al RPC decrement_stock.

Email

Para pagos aprobados, intenta enviar un correo al cliente y otro al negocio, evitando repetirlos con email_sent.

Riesgo de configuración: si MERCADOPAGO_WEBHOOK_SECRET no está configurado, el código registra una advertencia y permite continuar. El estado de secretos desplegados no está acreditado por la evidencia local.

08 · Recomendaciones
Acciones de auditoría priorizadas. Este documento no implementa ninguna de ellas.
P1

Cerrar autorización en base

Revisar has_permission, RLS y matrices de roles con casos permitidos y denegados.

Validar con pgTAP y llamadas directas no autorizadas.
P1

Hacer reproducible la puerta de DB

Arrancar Docker, reconstruir una base local no destructiva para el flujo normal y ejecutar pruebas de esquema, RPC, RLS y transacciones.

Registrar health checks, logs y resultado de db:test.
P1

Endurecer la configuración del webhook

Confirmar que el secreto de firma exista en el entorno autorizado y que su ausencia sea un estado explícitamente bloqueante antes de producción.

Probar firma válida, inválida, replay y reintento idempotente.
P1

Conciliar seed y migraciones

Comparar referencias, permisos, módulos y datos deterministas contra el esquema desde una base vacía.

Validar reconstrucción repetida sin duplicados.
P2

Ordenar deuda y etapas pendientes

Separar lint histórico de regresiones nuevas y mantener el roadmap del ERP con puertas por módulo.

Publicar checklists de contrato, auditoría, reversa y observabilidad.
